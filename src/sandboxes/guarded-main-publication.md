# Conditional root-workspace publication

Scope: the deterministic `pushSandboxToGithub` caller used by `provisionSandbox` / `setup-sandbox`. Existing work: checkpoint D, app #2116/#2140. No new legacy job is added.

The publisher observes exactly `refs/heads/main` with `git ls-remote --exit-code` before preparing the root commit. A successful no-match response means the branch was absent; transport/auth errors or malformed output stop publication. After staging/committing, it captures a specific local commit and verifies that commit contains the observed remote tip. This rejects a stale sandbox rather than adopting the latest remote as permission to replace it.

One push uses `--force-with-lease=refs/heads/main:<observed-sha>` and the captured commit SHA as its source. For an absent branch the expected value is empty, meaning create only if still absent. The explicit value is never refreshed or inferred from a tracking ref at push time; background fetch cannot weaken it. Moving local HEAD after validation cannot change the pushed commit. There is no fetch/reset/rebase-abort, automatic newer-tip retry, or unconditional-force fallback.

On rejection or unknown acknowledgment, the publisher returns false and keeps its local commit/files. Provisioning now propagates that outcome. Setup follows the existing snapshot-and-persist path, then reports unconfirmed publication with the recovery snapshot ID before its existing shutdown. It does not claim GitHub publication succeeded. The existing task disables automatic retries. Snapshot retention is the existing seven days, not a new permanent draft store. Snapshot creation/pointer-persistence availability remains the existing lifecycle dependency; the publisher itself does not discard/reset local work.

Synthetic tests use real Git repositories and two local writers, with Git protocols limited to local files and provider/agent preparation mocked. They cover ordinary and already-committed work, a newer competing push, an already stale sandbox, missing-main creation and creation races, remote-read failure/malformed output, background tracking refresh, lost acknowledgment and concurrent local HEAD movement. Caller tests verify outcome propagation and recovery snapshot before reporting failure/shutdown. No customer repository or hosted sandbox is exercised.

This does not protect arbitrary sandbox filesystem writes, detached shell jobs, direct SDK writers, or AI-delegated org-repository pushes in `pushOrgRepos`. That helper runs earlier in the existing preparation sequence and still has its own unconditional-force instruction; the root branch guard cannot undo or protect those separate writes. Remote-identity/permission validation, including existing Tasks #82, remains independent. No authentication, credentials, access, Context provenance or material-association contract changes are included.

After release, a stale root-workspace publisher stops rather than replacing newer remote work. Setups that previously forced a divergent root snapshot onto main will now require reconciliation. Uncontended setup still publishes and returns the same successful task result. The Tasks repository automatically deploys Trigger workers on main; this feature PR is not merged or manually deployed as part of implementation. Hosted acceptance and actual worker-version verification are separate from local tests/CI.
